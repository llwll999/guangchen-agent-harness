# 笔试题与验收清单

来源：[2026年 Agent harness 技术笔试题](https://ucnk0qbix8zv.feishu.cn/docx/BQkad8EA6oXK1rxuqbec9ycXnbd)。2026-10-03 读取，页面显示 9 月 27 日修改。

## 提交约束

- 一周内完成。若从 2026-10-03 起算，计划在 2026-10-10 前完成；以招聘方实际约定为准。
- 代码通过 GitHub 链接提交，不提供 API 密钥。
- 允许 AI 辅助，核心 Agent Runtime 自行实现，不依赖 LangGraph、OpenHands、OpenClaw 等 Agent 框架。
- 需要真实 LLM API；mock 可以用于 search 和自动化测试，不能替代真实模型验收。
- 面试会逐行过代码，需要理解所有提交的实现。
- 架构设计共五个模块，每个模块选一道回答。

## 编程题验收

| 要求 | 可观察的验收方法 |
| --- | --- |
| 用户输入 → 模型决策 → 工具 → 再决策 → 最终回答 | 一次任务连续调用 calculator、todo，再返回结果 |
| 至少三个工具，必须有 todo | 注册 calculator、search、todo，提供名称、描述、参数 Schema |
| 根据 Schema 自主调用 | 真实模型根据工具定义返回调用，Runtime 不使用关键词路由 |
| 输出解析 | 解析最终答案、工具调用；保留模型公开返回的简短说明，不索取隐藏推理链 |
| 独立 session | 同一用户两个窗口分别维护对话和 todo，切换后可继续 |
| 持续对话和追问 | 纯聊天追问，以及引用前一个工具结果的追问 |
| 最大轮次 | 模型持续请求工具时有限步终止，并保存可继续的完整记录 |
| 基础压缩 | 保留最近完整对话轮次，较早历史压缩；工具调用和结果不能被截断成孤立消息 |
| 基本异常处理 | 未知工具、无效 JSON、参数错误、工具异常、模型请求失败 |
| 工具 trace / 日志 | 每次调用可追踪名称、调用 ID、状态、耗时，不记录 API 密钥 |
| 测试 | 自动测试以上功能，真实模型烟雾测试单独标注 |
| README | 运行方式、系统设计、memory 召回时机和放置方式 |
| AI 记录 | 实际使用的提示、问题、修复与验证，区分已验证和未验证 |

## 架构设计原题

### 模块一：Context / Performance

1. 大模型面对第一轮长窗口或多模态输入时，first token 会显著变慢。有什么快速/低成本/用户体验也不差的方案？从 5–10 秒稳定压缩到 2 秒。
2. 一个 session 连续聊了 200 轮，context 快爆了。你会怎么做压缩？如何确保压缩后的对话仍然流畅？

### 模块二：Memory

1. 和聊天 Agent 熟悉半个月后，用户问了一个以前问过的问题。Agent 如何做 memory 召回更合理？
2. 你理解的 Agent memory 经典框架是什么？它的发展趋势是什么，最头部的玩家在怎么做？

### 模块三：Task

1. 对于长程任务，大模型执行一段时间可能会忘掉目标，你知道哪些解决方案，有什么优缺？
2. 用户给 Agent 下达任务：每天早上 9 点根据昨天聊天情况做复盘总结。你会怎么设计？

### 模块四：Tool / Session Runtime

1. Agent 工具有同步和异步两类。异步工具不能让用户一直等，但结果依然重要。你会如何设计异步工具执行和完成通知？
2. 如果 session state 为 busy，此时用户又发来新消息，或者异步工具完成事件也到达，runtime 应该如何处理？

### 模块五：Agent Runtime 架构对比

1. Claude Code 的工具输出方式和国内 GLM / 豆包等 OpenAI-compatible function calling 有什么不同？他们各自这样设计的优缺点是什么？
2. OpenHands 的状态机设计有什么优缺？更优雅的实现方式是怎么样的？

## 一周安排

1. 理解消息协议与工具调用，写出循环和 calculator。
2. 实现 Schema 校验、todo、search，跑通真实模型。
3. 增加 session 持久化和隔离，验证追问。
4. 完成历史压缩、异常和日志，补边界测试。
5. 每模块选一道架构题，写自己的取舍和反例。
6. 逐行讲解，手写主循环，模拟工具失败和压缩后的追问。
7. 新目录复现运行，真实模型验收，整理 GitHub 提交。
