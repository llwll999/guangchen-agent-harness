# 面试官审查与修复报告

日期：2026-10-03。审查对象是本目录的最小 Agent Harness。结论：核心循环可解释，但初版在状态回滚、引用隔离、预算和召回上存在真实缺陷，现已修复；仍是本地同步原型。

## 如何验证

先写反例，再跑原版确认失败，然后修复并跑原有测试。新增 19 个测试方法，合计 41 项通过；这是方法数，不是用户样本数。固定种子随机测试另包含 500 次 CRUD 操作，分页测试包含 100 条特殊字符待办。所有测试使用脚本模型或 mock HTTP，真实 LLM 验收尚未运行。

```powershell
.\.venv\Scripts\python.exe -m unittest discover -s tests -v
```

首次 14 个审查方法中，仅随机 CRUD 方法通过；带子案例的输出为 16 个失败断言和 3 个类型错误。随后新增 5 个集成/边界方法。列表分页是新增能力，首次不支持分页参数不算原有接口的 bug。

## 已复现的正确性缺陷

### 1. 高：失败工具仍然留下修改

反例：自定义 handler 先 append 一条待办并递增 ID，再抛 ValueError。原版返回 `ok:false`，但 state 中已经存在“ghost”，最终会保存到数据库。用户和模型都以为失败，业务状态却发生变化。

修复：handler 在深拷贝上执行；结果和状态都能编码后，才替换本轮内存 state。异常就丢弃副本。测试也覆盖 handler 返回 object()、将 NaN 写入状态，以及同一批“失败写入→成功写入→模型失败”：只有成功的那条保存，两个调用仍各有一个 tool 结果。

这只回滚本地内存。外部支付、邮件、文件写入不能依靠 deepcopy 撤销，必须另设计幂等与执行记录。每个调用独立提交，不是整批调用全成或全败。

### 2. 高：Schema 和结果共享可变对象

反例 A：修改 `definitions()` 返回的 expression.maxLength，执行端 Schema 也跟着变化。反例 B：注册后修改调用者的 schema，也能放宽校验。反例 C：修改 todo.add 返回的 item.text，state 中待办同步被改。

修复：注册和输出 definitions 都复制 Schema；成功提交的 state 与返回 observation 分别复制。frozen dataclass 只禁止字段重新绑定，不能冻结嵌套 dict。对应三个回归方法验证所有边界。

### 3. 高：同进程两个 store 可同时写同一会话

反例：两个 SessionStore 打开同一数据库，一边持有 claim，另一边仍可进入相同 user/session。初版每个实例各有自己的锁表，可能同时读到旧状态，后保存者覆盖先保存者。

修复：规范化数据库路径，使用类级 guard 保护 `(path,user,session)` 活动集合。检查和插入在同一临界区，finally 删除标记；不同 session 仍可运行。200 次异常退出测试检查标记释放和没有持续增长的锁缓存。

边界：不同进程、数据库硬链接别名和绕过 claim 的直接 load/save 不在保证范围。多个独立 CLI 同时写同一数据库仍不支持。

### 4. 中：预览再次转义后超预算

反例：结果由反斜杠、引号、换行、制表符、NUL 组成。初版先截取序列化结果的前 2500 字符，再把它放进 preview 字段二次编码，实际得到 3790 字符，超过 3000 上限。

修复：对最终 JSON 编码后的长度做二分搜索，寻找可放入 preview 的最长前缀。单调性来自前缀增长只会增加转义后长度。所有一般工具观察保留 `truncated:true`，不能把 preview 当完整结果。

### 5. 中：旧长回答末尾事实召回不到

反例：旧 assistant 回答以 400 次“普通背景。”开头，末尾才写“海鸥项目密码为蓝鲸777”；几轮后追问密码。初版只检索每条消息前 350 字，或者凭其他公共关键词召回该轮却未带回答案。另一个反例是 8 次工具行动说明把最终日期答案挤出摘录。

修复：对完整 user/assistant 文本打分；摘录优先保留用户问题和最终答案，在查询命中位置选窗口。摘要不再用大量行动说明挤占最终答案。预算缩小时复用已算的分数。

边界：关键词匹配仍不理解“之前那个”，不管理事实版本，也不保证选中多处命中的最佳片段；只存在于工具结果中的细节不会直接参与召回。两个召回测试只证明对应反例修复，不代表通用记忆准确率。

### 6. 中：JSON 容忍模糊参数和无穷数

反例：`{"action":"add","text":"甲","text":"乙"}` 默认解析时悄悄保留乙。自定义 number 工具收到 NaN、Infinity、1e999，执行端仍会调用 handler，后者可以返回普通文本掩盖异常输入。

修复：共同使用 strict_loads。object_pairs_hook 在构建 dict 前检查重复键；parse_constant 拒绝特殊常量；parse_float 检查数值有限。Schema 校验发生在其后。HTTP 响应也使用此解析器，重复 choices 不能悄悄覆盖。

### 7. 低：输入类型和内存数据库报错不明确

反例：user=None、session=1、text={} 在 strip() 处抛 AttributeError；CLI 虽然输入都是字符串，库接口也应明确校验。`:memory:` 建表连接随后被关闭，下一次连接是另一座空库，无法持久化。

修复：字符串类型先于 strip/len 校验，返回预期 ValueError；构造器明确拒绝 :memory:。它们不会被包装成模型失败或谎称已保存。

## 能力优化：待办结构化分页

初版超长 list 只返回原始 JSON 字符串前缀，剩余条目仍在 SQLite，但模型没有可靠方法读取尾部。现支持 `offset` 和 `limit`，返回 items、total、next_offset；每页按序列化后的 2800 字符预算提前结束，Runtime 的 3000 字符上限通常无需再截断。

```json
{"action":"list","offset":0,"limit":10}
```

如果 next_offset=2，下一次传 offset=2；如果为 null，读取结束。用 100 条各 200 字符、含五种转义字符的待办验证逐页结果与原始列表完全一致，无丢失、重复或死循环。空列表、末页、负 offset、零 limit、bool limit 和写入动作误用分页参数也有覆盖。

分页是有成本的：读完很多页消耗模型步数，一轮最多 8 次模型决策时可能只能读部分。分页期间修改列表会让 offset 失效；本版不提供快照。应保持预算并允许追问继续，不能为了展示“读完”取消熔断。

## 随机测试验证什么

种子 20261003，500 次 add/complete/delete。输入包括中文、emoji、引号、反斜杠和换行。独立 reference dict 保存预期状态；每步比较待办内容、顺序、ID、完成状态和 next_todo_id，失败操作必须不改变 state。这覆盖组合行为，避免只断言“返回值等于实现里刚写的值”。测试可重复，不引入第三方测试依赖。

## 面试官仍会指出的缺点

1. **真实模型行为未知**：目前证明 Runtime 机制，不证明模型在不同措辞下能正确选择工具。需要真实 API 固定样本、多次运行、轨迹和状态判定。
2. **可靠性边界**：没有跨进程租约/CAS、durable inbox、外部工具幂等、断点恢复或完整任务 deadline。30 秒是单次网络超时设置，不能宣称整个 Agent 30 秒内结束。
3. **记忆质量**：字符预算不是 tokenizer，摘要有损，召回同义词与冲突事实处理弱；任意长历史都保存，数据库与深拷贝成本增长。
4. **可观测性**：trace 有步骤、工具结果状态和工具耗时，没有服务商 token 使用量、模型耗时或完整生产指标。摘要/日志不保存原始工具参数，无法单靠 trace 做精确重放。
5. **扩展与安全**：user ID 只是命名空间；工具是受信任的本地代码，没有权限模型、沙箱或通用 handler timeout。提示词把资料标成数据有帮助，但不构成防注入安全边界。
6. **产品完整度**：search 仅三条 mock 文档；无流式交互；generic 大结果缺少原文档案；分页缺少快照版本。这些是明确取舍，不伪称生产已实现。

建议的下一步顺序：先真实 API 验收，随后拆分只读历史与可变业务 state、加入 token/耗时指标，再按服务器需求做数据库版本和任务队列。保持项目能逐行解释，比一次加入很多未经验证的框架更重要。
