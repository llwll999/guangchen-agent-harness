# 五道架构题讨论稿

每模块选一道：一选 2，二选 1，三选 1，四选 2，五选 2。下面给出可以讨论和反驳的设计，不代表候选人的个人经历或已实现的生产能力。提交前应改成自己能解释的取舍。

## 一：连续 200 轮的 context 压缩

我先区分“可恢复的历史”与“本次送模型的 context”。全量事件持久化，context 只是有限投影。近期若干完整用户轮次、当前任务目标、未完成事项和已验证事实优先；大工具输出保留结果摘要与原文引用。工具调用及其结果是一个原子组，不能按最后 N 条消息切片。

预算临近阈值时，把较旧轮次变成结构化摘要：目标、约束、关键事实、决定、未决事项、原文事件 ID。摘要写明来源，不把用户/文档内容升级为系统指令。新信息与旧事实矛盾时保留版本、时间和来源，避免“覆盖后忘记为什么变了”。压缩后的问句若依赖旧细节，再按当前问题召回原文。不能只摘要再摘要，长期递归会累积错误；应定期依据原始事件重建。

判断对话是否流畅要有压缩前后同题评测：代词追问、旧日期、用户修正、工具结果引用和多窗口隔离。测事实准确率、未决任务保留率、token 成本与延迟；召回不足时问一句确认，比编出连续感更可信。

本项目只实现截取式摘要、最近完整轮次和关键词召回，验证了两百轮后可按“海鸥”命中旧记录；同义追问可能失败。下一步先改召回质量和带来源的摘要，而不是立刻引入复杂记忆系统。

## 二：半个月前问过的问题，如何召回

用户问同样的问题，可能想复习旧答案，也可能想要更新答案。先以当前问题和最近对话构造查询，检索用户有权限的历史；当前窗口的记录优先，跨窗口记忆需要产品明确的用户级作用域。不能因为两个窗口属于同一人，就默认所有临时任务可互相注入。

检索可组合关键词（名称、日期、编号）与语义向量（同义表达），然后按相关性、时效、可信度去重/重排。稳定偏好与某次临时决定分别存储；动态事实带时间和失效条件。以少量带原文引用的事实卡片放在 context 的数据区，保留最近对话，并用明确提示防止把历史中的指令变成新的权限。

若命中以前的答案，先判断是否仍然有效：对于“我上次选择哪个方案”，回答过去的决定；对于“现在该选哪个方案”，旧答案只作背景，还需更新资料。没有命中不能说“你从没问过”。用户纠错应新增修正记录并使旧版本失效；删除记忆时还需更新检索索引。

本项目召回发生在每次模型请求前，仅同 session，旧轮次关键词命中最多两条，作为 user 资料放在近期对话之前。它成本低且可解释，但不适合作为半个月跨话题语义召回的最终方案。

## 三：长程任务忘掉目标

我把目标和完成条件持久化为独立 task state，不寄希望于模型一直记得第一条长提示。保存当前计划、完成证据、下一步、阻塞项和剩余预算；每轮构造 context 都放入精简目标和当前子任务。todo 可以表示进度，但仅有“打钩”不足以证明目标真的完成。

三个方案可以组合：固定目标提醒实现简单，但会增加重复 token；分阶段计划和检查点利于恢复，但计划可能过时；独立评估器或规则验收可发现偏航，但会增加模型费用，评估器也可能误判。对代码任务，测试和产物比模型自己说“完成了”更有说服力。重规划必须回到目标和证据，而不是在旧计划上无限追加步骤。

每个阶段设步数、时间、费用或无进展上限。用户更新目标时记录目标版本；旧版本上的进行中动作不能直接当成新目标下的完成证据。外部工具写操作用业务幂等键，恢复时先查询完成记录再重试。状态只存可验证的行动和简短决策说明，不依赖长篇内部推理。

本项目有执行步数、todo 和最初请求线索，没有独立 task 表、阶段验收器或断点恢复。这些是生产设计建议，不能在面试里声称已经实现。

## 四：busy 时收到新消息或异步工具结果

一个 session 应只有一个状态写入者。新消息和异步完成事件先写入有序 inbox，包含 event_id、session_id、task_id、tool_call_id 和目标版本；worker 再串行处理。busy 是运行状态，不是丢弃输入的理由。UI 及时确认“消息已接收”，新输入默认排队，停止/纠正目标在安全边界优先处理。

模型请求已发出时到达的新消息不会神奇地改变这次输入快照。返回后检查版本：如果用户取消或修改目标，旧响应可留审计记录，但不能继续执行过时写操作。已经发生的外部副作用要明确反馈，不能声称取消就从未发生。

异步工具先返回 pending 和 job ID，worker 不持续占用模型调用；完成事件按关联 ID 回填原任务，再决定是否续跑或只发通知。同一个事件重复投递时，以 event ID 去重；取消任务的迟到结果不能恢复已取消目标。队列可按至少一次投递设计，状态写入与消费标记放同一事务，通知用 outbox，避免“状态已完成但通知永远丢了”。

测试重点是竞态：用户消息与工具完成同时到达、重复结果、取消后完成、崩溃后重放。当前活动会话标记支持同一进程、同一规范化数据库路径的多个 store；跨进程多 worker 仍需数据库版本或租约。当前实现对 busy 返回可重试提示，工具全同步，没有 inbox 或异步完成通知。

## 五：OpenHands 状态机的优缺与改进

需要先说明版本。我讨论旧 AgentController/EventStream 设计的取舍，再参考新 SDK，而不是把两者说成一个未变化的系统。OpenHands 官方 2025-09-04 迁移说明介绍了旧 pub/sub EventStream，并指出消息顺序及线程/异步复杂性，提出同步 conversation 执行的新方向。[官方迁移说明](https://www.openhands.dev/blog/the-path-to-openhands-v1)

显式状态和 Action/Observation 事件的优点是生命周期可检查，工具反馈可关联，暂停、恢复和审计更清晰。我的判断是，真正困难的通常不是状态枚举数量，而是多个回调共同推进 state：哪个事件先到、谁能写、旧 action 的结果还能否推动当前任务。把工具执行、预算控制、用户输入和子任务都放进一个控制器，还会增加耦合。

我的改进是保留状态机但收紧所有权：每 session 一个串行 reducer，`(state, event) → (new_state, effects)`；模型调用和工具执行作为 effect 由独立 executor 执行，结果以事件回到 inbox。状态迁移逻辑可以离线重放，executor 管超时与幂等，长任务借助持久化检查点。代价是事件版本、恢复和 effect 去重都需要额外设计；简单本地任务可先用清楚的同步循环。

当前官方 SDK 文档已经区分 Agent、Conversation、Tools、Workspace、Agent Server，并介绍独立事件与基础状态的持久化。因此“更优雅”应针对具体旧版本或具体竞态提出改进，不能笼统说 OpenHands 没有模块边界。[当前架构](https://docs.openhands.dev/sdk/arch/overview)，[持久化设计](https://docs.openhands.dev/sdk/guides/convo-persistence)

本项目采用同步循环和独立 store，容易逐行解释；它不具备上述 durable inbox/reducer。面试可用本项目解释最小运行链，再讨论为什么扩展到异步和多进程需要新的机制。

## 每题应能回答的反问

- 压缩后用户问“之前那个”，关键词召回不命中怎么办？
- 两个窗口是否应该共享用户偏好，哪些信息不应该共享？
- 模型说任务完成，如何用证据判断？
- 取消之后工具仍然成功，应该告诉用户什么？
- reducer 本身容易测试，但 executor 已写入外部系统后崩溃，如何防重复？

为每题准备一个具体场景和一个失败反例，比堆术语更有用。
