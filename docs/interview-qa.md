# 项目面试追问与回答讲解

这份模拟问答结合本项目代码和已有大模型开发面试笔记编写，供理解、手写和演示；不是光辰智能已出过的面试题，也不是可以冒充个人经历的标准答案。涉及生产设计时明确区分本版实现与下一步。

## 一、主循环与协议

### 1. 用一分钟介绍项目，为什么没有框架？

**考察**：是否理解自己写了什么，而非背组件名称。

**可回答**：这是最小 CLI Agent，用真实模型返回 function calling 决定动作，我写 Runtime 执行工具并把 observation 回传，循环到最终答案或预算停止。model 适配网络协议，registry 管工具与校验，store 管用户/窗口独立状态，context 构造有界输入。题目要求自写核心运行循环，且小实现容易定位协议和状态问题。41 个离线测试覆盖机制，真实 API 仍待验收。

**追问**：“相比成熟框架少什么？”——没有 durable task、异步事件队列、权限系统、生产 tracing 和通用工具超时；不宣称框架不如自己代码。入口：`runtime.py:Agent._run`。

### 2. Agent 与工作流区别在哪？你是不是用关键词路由？

**讲解**：生产路径由模型选择最终回答或工具调用，Runtime 不根据“计算”二字写 if 路由；工具内部 search 的关键词检索不等于 Agent 路由。工作流可把已知步骤写成固定代码，确定性强；Agent 适合步骤需依据 observation 决定的任务。不是每个业务都值得引入 LLM。

**追问**：“为什么权限也不给模型判断？”——模型提出动作，代码决定允许执行什么。此版白名单和参数校验已实现，业务授权未实现。参考滴滴架构题的规则与 Agent 分工。

### 3. assistant 说‘正在计算’，为什么不能结束？

**讲解**：`content` 与 `tool_calls` 可以同时存在；有调用时 content 是行动说明，需先执行工具、追加对应 tool 消息再请求模型。无调用且合法非空 content 才完成。真正的完成标志由响应结构和 finish_reason 决定。

手写这个最短协议链：

```json
[
  {"role":"assistant","content":null,"tool_calls":[{"id":"c1","type":"function","function":{"name":"calculator","arguments":"{\"expression\":\"6*7\"}"}}]},
  {"role":"tool","tool_call_id":"c1","content":"{\"ok\":true,\"result\":{\"value\":42}}"},
  {"role":"assistant","content":"结果是42。"}
]
```

**追问**：“省略 assistant 调用直接传 tool 结果呢？”——没有明确关联来源，可能被服务商拒绝。对应 `parse_message` 和 `_run` 的消息追加。

### 4. 一次模型给两个调用，第一个失败怎么办？

**讲解**：先验证完整调用结构，再按顺序执行每个 handler，每个 ID 都有一个观察。业务失败返回 ok:false，后面的独立调用仍执行；下一次模型能看到失败并纠正。本版没有批次事务，也不会自动判断调用之间的数据依赖。要用前一调用结果构造后一调用参数，模型应在收到 observation 后新一轮决策。

**追问**：“先 add 成功、后 complete 失败呢？”——add 保留，complete 的副本丢弃。`test_failed_write_then_successful_write_and_model_error` 验证更复杂的保存边界。

### 5. 最多八步，是最多八个工具吗？

**讲解**：max_steps 限制模型决策次数，单次响应最多八个调用，理论最多 64 个调用。最后一步仍执行该响应里的全部工具、配齐观察，再停止并给 max_steps 说明；成功工具不会因为没有最终回答而被撤销。重复 call ID 会在执行前停止。

**追问**：“能保证 30 秒结束吗？”——不能，网络超时、重试、多个模型轮次都耗时，handler 无通用超时。生产要给总 deadline、费用和无进展预算，这些本版尚未实现。

### 6. 为什么不用 Prompt 输出 Thought/Action 字符串？

**讲解**：文本模板有漏字段、拼错参数、内容与动作混合等风险。function calling 提供结构，但仍需执行端 parse、Schema、安全控制、预算与 observation 配对。Runtime 保存可验证动作和结果，不需要获取或持久化隐藏思维链。带 reasoning_content 的服务商协议当前拒绝，接入时需要专门适配。

**追问**：“Schema 能保证模型不犯错吗？”——不能，它约束格式，不保证业务语义或授权。参考腾讯工程化 ReAct 问题。

## 二、工具、JSON 与状态

### 7. JSON 能解析，为什么还要 Schema 和业务校验？

**讲解**：三层职责不同。strict_loads 拒绝重复字段和非有限数字；Schema 检查类型、必填、长度、额外字段；handler 检查业务前提，例如空白 text、待办是否存在和 100 条上限。`{"action":"complete","id":true}` 在 Schema 层失败，合法但不存在的 ID 在业务层失败。

**追问**：“为什么 1e999 也拒绝？”——它语法看起来像 JSON 数字，但转换成 float 会变成 inf。`parse_float` 需检查 isfinite，而不只拒绝 NaN 字面量。

### 8. deepcopy 为什么能解决‘失败却写入’？

**讲解**：handler 拿到 working 副本，原 state 不受中途写入影响。执行成功后检查 result 与 working 可序列化，再复制状态并提交回原 dict；异常不提交。提交给状态的对象和返回 observation 也分开，防止调用者改结果进而改状态。

**追问**：“这是数据库事务吗？能撤回 HTTP 写入吗？”——都不是，只是本轮本地状态的提交边界；SQLite 保存是另一个边界。HTTP 要幂等和执行记录。成本是复制全历史，优化方向是只复制可变业务状态，并把只读 history 留给 Runtime。

### 9. frozen dataclass 已不可变，为什么 Schema 还要复制？

**讲解**：frozen 限制 `tool.schema = 新对象`，不限制 `tool.schema['properties']['x'] = ...`。初版 definitions 与内部共用 dict，外部能改变执行限制。注册时隔离调用者，输出时隔离消费者，两处都要复制；只做一处仍会有漏洞。位置：`ToolRegistry.register/definitions`。

**追问**：“只用 dict.copy() 呢？”——浅拷贝仍共享 properties 等嵌套对象，回归测试修改的正是嵌套 maxLength。

### 10. calculator 用 AST 就绝对安全吗？

**讲解**：安全性来自节点和运算符白名单，不是 AST 名字本身。仅数字、正负号、五种二元算术，禁止名称、函数、属性、下标和乘方；限制 160 字符、64 节点、绝对值 1e12 和有限数。type(value) 精确判断排除 bool。不同资源风险需各自限制。

**追问**：“0.1+0.2 精确等于 0.3 吗？”——float 存在精度误差。演示计算器可以接受，金额应使用 Decimal/整数最小货币单位及明确舍入，不拿 float 计算金额。本版也不支持科学符号以外的复杂数学函数。

### 11. 超长结果为什么用二分，直接截 2500 字不行吗？

**讲解**：preview 自己还是 JSON 字符串，原来的反斜杠和引号会再次转义。初版 2500 字前缀生成 3790 字结果。二分对最终 json.dumps 长度判定，前缀越长，编码长度不会变短，满足单调性。O(log N) 次试编码，最终保证 observation 不超 3000 字符。

**追问**：“预览本身是合法原始 JSON 吗？”——外层 JSON 合法，preview 只是可截断文本，不可当完整业务对象。需要精确读取的数据应分页或存原文引用。

### 12. todo 的分页如何保证不会漏数据？

**讲解**：offset 从 0 开始，最多 limit 条，按最终编码预算提前停，next_offset 等于 offset 加本页条数。total 表示原列表总条数，只有 next_offset=null 才结束。100 条转义字符测试逐页拼接后与原列表全等；还断言 offset 严格增长，防止空页循环。

**追问**：“读第二页前删了第一页的一条呢？”——offset 可能漏项。本版保证只读期间分页，不提供快照；服务器应增加版本/快照游标或按单调 ID 的 keyset 分页，并定义更新的可见性。一轮受 max_steps 限制，不一定读完全部。

## 三、会话、并发与失败恢复

### 13. SQLite 有事务，为什么还会丢更新？

**讲解**：两次 load 各自合法，两次 save 也各自原子；但如果都从旧 state 修改，后写覆盖前写。事务保护的是单次保存，而整个 load→模型网络→工具→save 跨很长时间。活动集合让同进程同会话只有一个 owner；网络期间不占 SQLite 写事务，其他 session 不必等。

**追问**：“多进程怎么做？”——版本 CAS 能检测旧版本覆盖，租约/单 writer 能避免并发执行；外部副作用还需业务幂等。不能仅加一个数据库版本就宣称 exactly-once。

### 14. 为什么活动集合是类变量？会不会无限增长？

**讲解**：实例变量无法覆盖两个 store 对象，所以同进程共享集合。key 加规范路径避免不同数据库碰撞；guard 让检查与插入成为原子操作。进入只记活动项，finally 删除，空间跟正在运行的会话数相关，不跟历史 session 数相关。

**追问**：“异常了还能释放吗？”——上下文管理器 finally 覆盖返回和异常；进程强杀时内存消失，没有永久进程内标记。但跨进程互斥仍不存在，数据库硬链接路径别名也不在承诺内。

### 15. 工具成功后模型超时，用户重试会不会加两条待办？

**讲解**：本版在 ModelError 后仍保存此前成功的本地操作，并向用户说明。重复调用 ID 只防同一 run 的重复 ID；重试是新 run，若模型又 add，会再添加一条。不同 ID 但相同业务参数也不去重，因为用户可能确实要两条。

**追问**：“真正幂等怎么实现？”——用户请求有 request_id，写操作按明确业务粒度生成 idempotency_key，执行账本保存 pending/succeeded 和结果；重试查询账本。外部服务也需接受幂等键或查询对账。不能靠比较 text 就自动删除用户意图。

### 16. 模型失败、工具失败、进程被强杀分别保存什么？

**讲解**：工具失败丢弃该工具副本，形成 ok:false 观察；模型失败结束本轮，提交此前成功的工具与历史；强杀/Ctrl+C 在最终 save 前发生，本轮内存操作全部丢弃，之前数据库已提交轮次仍保留。若强杀发生在 SQLite 提交后、回答展示前，状态可能已经保存但用户未看到反馈。没有外部工具断点恢复。

**追问**：“为什么不每步都保存？”——可以缩小崩溃损失，但需处理未配齐工具消息、pending 调用、恢复去重和更高写入次数；需要完整检查点设计，不能只塞一行 save。

## 四、Context 与 Memory

### 17. 为什么按用户轮次压缩，不能取最后 20 条？

**讲解**：一个用户轮次可能有多次 assistant 调用和 tool 结果，消息切片会留下孤立 tool。turn_groups 把整条任务链作为组；预算不够就移除旧完整组，当前组超限则停止。压缩模型输入不删除 SQLite 原始历史。

**追问**：“一次当前任务就 50 条消息呢？”——宁可 context_limit 提示拆分或提高预算，也不静默剪断协议。更复杂系统可生成检查点，在工具调用完成边界做压缩。

### 18. 两百轮后如何召回第 21 轮？为什么要检索原文？

**讲解**：在每次模型调用前，以当前问题提取关键词，对旧轮次完整 user/assistant 文本打分，选两条并带 turn 编号；同分优先较新。再从用户问题和最终答案中截命中窗口，放到稳定 system 后的“历史数据”消息。原文先参与检索，避免先截前缀再检索造成不可恢复的信息丢失。

**追问**：“如果问‘之前那个项目’？”——关键词弱，可能召回不到。应利用近期指代解析、语义检索和澄清；本版没有这些。参考腾讯记忆和企业级项目压缩笔记，但不声称已实现向量记忆。

### 19. 长期记忆、短期上下文、todo 是同一种东西吗？

**讲解**：SQLite 保存当前 session 全量历史，是原始事件存储；最近完整轮次是有限工作上下文；todo 是结构化业务状态。摘要是历史投影，不能反向覆盖原始事实；精确 todo 以工具/数据库为准。用户稳定偏好与临时任务还需不同作用域、来源和失效策略，目前没有单独用户级偏好记忆。

**追问**：“用户把十月十日改为十一月一日？”——新原文会保存，召回同分时更近优先，但没有结构化事实版本管理，仍可能旧新一起出现。生产应记录修正关系和有效时间，不能假装当前排序解决所有冲突。

### 20. 摘录当 user 数据就能彻底防 Prompt 注入吗？

**讲解**：标为数据、保持 system 规则能降低指令混淆，但大模型可能仍受恶意文本影响。代码层的工具白名单、Schema 和操作权限才是实际执行边界。当前没有鉴权和风险操作确认，也没有把用户授权绑定到每次写入，所以不具备通用防注入保证。

**追问**：“注入文本让模型清空待办呢？”——不能只测回答有没有复述恶意文本，应查是否发生未授权写入；真正验收要用真实模型和业务授权策略。本版只证明参数与本地状态机制。

## 五、评估、性能与升级

### 21. 41 个测试全过，Agent 成功率是多少？

**讲解**：不能推出真实任务成功率。确定性测试给模型预先排好的返回序列，证明 Runtime 对该序列的执行机制；HTTP mock 证明请求/响应处理。真实任务需固定任务集、预期最终 state 和允许工具轨迹，覆盖普通措辞、多步、纠错、长历史、隔离与恶意输入；每样本重复运行，报告成功数/总数与模型版本。

**追问**：“结果、过程、成本怎么测？”——结果看状态与事实正确性；过程看工具是否合规、重复写入和配对；成本看 token、延迟和调用数。用失败分布指导改进，不虚构笔记示例中的提升百分比。参考腾讯 Q14、滴滴 Q6–9。

### 22. 换模型或改 Prompt 后怎么验证？

**讲解**：固定工具、数据、预算，先只改一个变量；跑协议合同测试和真实任务回归，记录输出格式、工具选择、状态准确率、延迟、费用，再决定升级。新模型的 finish_reason、思考字段、Schema 支持和错误码可能不同，不能因为标 OpenAI-compatible 就认定完全兼容。

**追问**：“temperature=0 就稳定了吗？”——不能当工程保证。依然需要执行端约束和回归。当前没有设置温度，也没对真实模型稳定性做统计。关键写入的确定性应由代码和业务策略保证。

### 23. 这份代码性能最先优化哪里？

**讲解**：先量测，再优化。当前每个工具深拷贝全 state，历史越长成本越高；每次 context build 扫全历史，多个模型轮次重复扫描；SQLite 把完整 session JSON 重写。优先拆只读历史与业务状态，对历史增量索引/缓存关键词，按事件表追加存储，保持完整协议投影。当前已把一次 build 内预算循环的打分提到循环外，没声称有完整索引。

**追问**：“直接并发所有工具能提速吗？”——有依赖的写操作会竞争状态。只有无共享写入的独立工具才适合并行，结果顺序和调用 ID 必须保持。本版选择串行以降低复杂度。

### 24. busy 输入和异步工具结果怎么处理？

**讲解**：当前 busy 立即拒绝，不接收和持久化排队消息，所有工具同步。生产可用 session inbox 和单写者，把用户消息/完成事件统一成带 event_id、task_id、目标版本的事件；完成后检查是否取消或目标变化，再决定续跑。通知可用 outbox，重复事件去重，迟到结果不能复活已取消任务。

**追问**：“回调更新 state 不就行了？”——多个回调并行会产生乱序、旧目标写入和重复副作用。先明确状态所有权，再设计 executor 与串行 reducer。这里是架构方案，不是当前能力；对应架构题第四、第五题。

## 六、逐行讲解和模拟面试

面试官指一行时，按“输入→作用→失败→取舍”讲，避免只把语法翻成中文。例如：

- `Draft202012Validator(...).validate(args)`：输入已严格解码对象，用工具 Schema 验证类型/字段；失败返回 invalid_arguments，handler 尚未执行；业务存在性留给 handler。
- `state.clear(); state.update(committed)`：原 dict 身份不变，内容来自成功并验证的副本；调用前已完成所有容易失败的编码/复制；它是内存提交，不是持久化或外部回滚。
- `with self._guard`：保护活动集合检查与插入，不能把整个网络调用放在全局 guard 中，否则不同 session 也会串行。
- `with closing(sqlite3.connect(...)) as db, db`：外层负责关闭连接，内层事务负责提交/回滚；仅 with connection 不代表关闭连接。
- `scores = ...`：使用完整文本，且一轮 build 算一次；之后预算减少复用分数；仍不是语义检索或模型 tokenizer。
- `middle = (low + high + 1) // 2`：取上中位数，配合 low=middle 的分支确保二分进展；条件检查的是最终外层 JSON 长度。
